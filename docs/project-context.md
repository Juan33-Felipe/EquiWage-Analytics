# EquiWage Analytics — Project Context

## Project Overview

EquiWage Analytics is a desktop Human Resources application focused on internal salary equity and external market competitiveness.

The application helps HR professionals import payroll data, compare salaries against market salary bands, identify salary gaps and internal inequities, simulate salary adjustments, visualize salary distribution and generate reports.

The application is currently in the frontend development stage.

The current goal is to build a complete and coherent desktop application interface. Real backend integration, database persistence, authentication and production data processing are NOT part of the current implementation stage.

Use realistic mock data whenever necessary to represent the application's future functionality.

## Target User

The primary user is an HR professional responsible for analyzing compensation structures and making salary decisions.

The interface should therefore prioritize:

* Clear presentation of data
* Professional enterprise appearance
* Easy comparison
* Clear identification of problems and salary gaps
* Efficient analysis
* Strong visual hierarchy
* Simple and understandable interactions

## Important UI Principle

The application must be developed as one coherent product, not as a collection of unrelated screens.

The existing Dashboard is the primary visual reference for the application.

When implementing a new interface, inspect the existing Dashboard implementation and derive its visual language from the actual code.

Reuse and maintain its:

* Typography
* Colors
* Spacing
* Component patterns
* Cards and panels
* Buttons
* Borders
* Border radius
* Shadows
* Icons
* Visual hierarchy
* Overall density and proportions

Google Stitch designs are only references for the intended content and general structure of an interface. They are NOT the final visual specification.

If a Stitch design contains incorrect, inconsistent or inappropriate visual decisions, do not reproduce them literally. Adapt or redesign those parts so the final interface follows the established Dashboard design system and makes sense for the specific purpose of the screen.

The final result should look like it belongs to the same application as the existing Dashboard.

## Development Constraints

For the current stage:

* Frontend only
* No backend
* No API integration
* No database
* No authentication
* No production data processing
* Use mock/static data when necessary
* Keep the code structure prepared for future backend integration
* Preserve the existing project architecture unless a change is genuinely necessary
* Reuse existing components whenever possible

The objective is to build the correct interface and user experience for the application, not simply reproduce a reference image.
